# Commerce implementation — 22 October 2026

The existing visual design/CSS is unchanged. This is a local, test-only commerce foundation, not an approval to sell. It cannot use live Stripe keys or accept live webhook events. No real transaction or email was executed during implementation.

## Runtime and storage

Use Node 22.13+ (verified here on 22.21.1; built-in `node:sqlite` still reports its experimental warning), one Node instance and a persistent local disk. No extra npm dependency. `DATA_DIR` defaults to `data`; SQLite `commerce.sqlite` uses WAL, foreign keys, immediate transactions, a 5-second busy timeout and owner-only DB/directory modes. Protect the entire data directory and backups with OS permissions, encryption and restricted machine access. Do not put any of them under public, dist or source control. Do not share this SQLite DB between hosts or run on ephemeral storage.

`server/migrations/001-commerce.sql` is applied transactionally on first opening and recorded in `migrations`. Existing source catalogue seeds the database once; subsequent changes use [ADMIN.md](./ADMIN.md), not edits to seed JSON. Existing local frontend changes have been preserved.

`products(id,data)` persists publish/archive state, integer EUR prices, categories, packs, version and licence metadata. `/api/catalog` returns a public allowlist without private file paths or pack membership. The frontend loads it before rendering, preserving local seed browsing as a fallback during API outages. Prices and item availability are always checked by the server at checkout. Category names added through the CLI appear in existing filters/board. Promotions can use actual price plus compare-at metadata; there is no coupon engine or scheduling yet.

Every order saves customer details, EUR cents, names, licences, file versions, exact English consent/terms/licence texts and timestamps. Legal content comes from shared `src/app/data/commerce-terms.json`, explicitly a draft: seller identity, fiscal treatment, retention and legal review are pending. The UI requires separate terms and immediate-delivery/withdrawal acknowledgements. Recording these drafts does not make the shop legally compliant. Custom licence metadata is not a commercial licence system; only the current personal-use text is supported.

Private STL sources come from `FILES_DIR` (default `private-files`) and per-product relative `file`. Before checkout they are copied to `DATA_DIR/versions/<sha256>.stl`, exclusively, with size/hash checks. Purchased copies are immutable by application convention and remain independent of later source/catalogue changes. Do not manually overwrite them. This validates storage integrity, not STL geometry, units or physical print quality.

## Stripe TEST setup (external actions still required)

1. Configure `.env` locally from `.env.example`: `APP_ORIGIN`, `FILES_DIR`, optional `DATA_DIR`, `STRIPE_SECRET_KEY=sk_test_…`, `STRIPE_WEBHOOK_SECRET=whsec_…`. Never paste secrets into chat or browser variables.
2. Add real validated private STL files and review catalogue/terms. Leave `COMMERCE_ENABLED=false` until ready for a test checkout.
3. Configure Stripe CLI/test webhook delivery to `POST /api/stripe/webhook` (dev API port 3001; frontend proxy forwards `/api`). Subscribe to `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, `checkout.session.expired`, `charge.refunded`, `charge.dispute.created`, `charge.dispute.closed`, `refund.created`, `refund.updated`.
4. Set `COMMERCE_ENABLED=true` only for test mode and restart. Run a real Stripe test session, SCA, cancellation, delayed success/failure, duplicate events, refund and closed-browser delivery. These external tests have NOT been performed.

Checkout is hosted, in EUR, using card and Bancontact. Eligible Apple Pay wallets use the card flow without a separate payment method type. Code compatibility and a simulated wallet payment/refund are tested; device-side rendering and authorization remain unverified. See [Apple Pay preparation and owner test](APPLE-PAY.md). REST requests pin Stripe API `2024-06-20`; configure endpoint payload version accordingly and validate against a real test account before opening. No automatic tax, VAT calculation or invoice service is implemented.

A browser request key is bound to an order fingerprint; replay uses the same stored order and stable Stripe idempotency key. A changed payload conflicts. Attempts older than 23 hours require a new browser attempt to avoid reusing Stripe idempotency after its retention window. Users can still intentionally make separate purchases; this is not duplicate-purchase prevention.

Webhook signatures use HMAC-SHA256 over the untouched body, constant-time comparison and five-minute timestamp tolerance, with support for multiple v1 signatures. Only test events are processed. An event receipt commits atomically with order/access/outbox transitions. External Stripe reads happen before that transaction and can safely retry. Session mode, store/order/client reference, session ID, expected total/currency and expanded PaymentIntent/charge are reconciled. Failed Stripe reads/mismatches return errors without granting access. Receipt uniqueness handles repeated/concurrent delivery. Paid states cannot regress on old expired/failed events; fresh charge state checks refunds/disputes even if those events arrive before the session. Unknown refund/order association returns retryable 409 rather than acknowledging lost work.

Refunds are initiated in Stripe Dashboard for now. A successful partial refund **suspends the entire order conservatively**; there is no line-level allocation. Full refunds and disputes revoke download tokens and cancel unsent email. Unexpired order tokens remain usable only to show the authenticated order status; unpaid/refunded/disputed orders never receive download links. Old paid events never reactivate these orders. Dispute resolution/reactivation and exceptional support decisions require an audited workflow still to implement; a closed dispute remains suspended. No automated refund-creation endpoint.

Run `node scripts/commerce.mjs reconcile` periodically to recover missed session events (up to 50 pending/paid orders per run, least recently updated first). Stripe webhook retry/replay remains important for unrelated refund/dispute events. A hosting scheduler, alerting and stale-order follow-up still require configuration. There is no deployment in this change.

## Delivery and email

The browser saves a private 24-hour order token in tab storage before leaving for Stripe; raw session IDs alone grant no access. If storage is blocked, checkout displays an error before redirect; email access URLs still work. Emails point to `/checkout?order=…&access=…`; the token is removed from visible URL/history when tab storage is available. Do not log query strings or bearer headers at the reverse proxy, CDN or analytics layer. Order APIs require a hashed, unexpired token. Paid orders issue renewable five-minute file-specific download URLs and check local status for every download. A file cannot be retrieved merely with another item's token, another session ID or a revoked order. As with all downloads, already downloaded copies cannot be revoked.

`POST /api/recover` returns the same accepted response for known/unknown addresses and queues links only for paid purchases (up to 20 latest orders); a 15-minute per-order bucket avoids repetitive recovery. The confirmation page contains the recovery form. Full client accounts/history are not implemented. General API rate limit uses actual socket IP (120 requests/minute/process), never arbitrary forwarded headers; a trusted-proxy deployment needs an explicit per-client limiter at the proxy.

Outbox insertion is atomic with payment. Email is **disabled by default** and no sent state is fabricated. Configure a verified Resend sender, `RESEND_API_KEY`, `EMAIL_FROM` and explicitly `EMAIL_SEND_ENABLED=true` only when ready to test actual delivery. Server startup then polls outbox every 30 seconds; `node scripts/commerce.mjs emails` runs one explicit batch. Acceptance by provider records sent; this does not claim delivery to inbox. A stable per-message provider idempotency key, 60-second sending lease and exponential backoff (maximum 8 attempts; then failed) permit retries and crash recovery. First dispatch renews email access lifetime to 24 hours even if configuration was delayed. Provider errors keep the message retryable and never claim success. Provider bounce/delivery callbacks, DNS SPF/DKIM/DMARC verification and alerts remain external work. Resend is the currently implemented configurable provider, not a generic SMTP adapter.

Pending outbox contains email recipient/text and a bearer link in clear text because it must be sent: protect DB/backups as secrets. API token records are hashed. Successful sends purge outbox payload immediately. Cancelled/failed payloads and expired tokens need a retention/purge job and incident procedure before production. Provider idempotency has a limited retention window; do not manually retry ambiguous old messages without checking provider records. Never alter a payload after its first dispatch attempt. A refund racing with an in-flight email may still produce a now-invalid link; downloads remain denied.

## Administration and statistics

Administration is a local authenticated-OS CLI, not an internet admin page. See [ADMIN.md](./ADMIN.md): CRUD products/categories/packs, private file publication validation, archive, order listing/detail, order-derived EUR gross/refunded/net-before-fees/tax statistics and audit. Protect remote machine access with SSH keys/MFA. Browser back-office, admin roles/sessions and operational email retry/reissue workflows remain unfinished. No optional traffic pixel or advertising analytics was introduced. Traffic/conversion analytics remain unimplemented; revenue statistics come from saved payment states.

## Backup and restore

- `node scripts/commerce.mjs backup /private/backups/new-name.sqlite` uses SQLite `VACUUM INTO` for a consistent snapshot including committed WAL state; destination must not exist. Encrypt and copy off-machine with separate access credentials.
- Also back up **all `DATA_DIR/versions`**, source `FILES_DIR`, validated legal/catalogue metadata and protected service configuration. Keep generations together. Never back up only the SQLite main file while live, ignoring its WAL.
- Restore drill: stop the app/workers, keep original damaged data aside, create a fresh private data directory, copy the coherent snapshot as `commerce.sqlite` and the matching `versions` directory. Do not reuse old WAL/SHM files. Set DATA_DIR/FILES_DIR to restored locations, run `node scripts/commerce.mjs check`, inspect admin orders and perform a test download and reconciliation before reopening access.
- Automated test creates a paid order and access rights, snapshots with `VACUUM INTO`, opens a restored database and verifies integrity/order snapshots/token counts. This proves local DB restoration only; production offsite restore and full asset restoration have NOT been demonstrated. No backup job or external destination was configured.

## Verification and limits

Business tests exercise actual temporary SQLite + local HTTP + signed webhook bodies with simulated Stripe/Resend: replay, EUR server prices, malformed bodies/consents/origin, private regular files, unpaid/async/out-of-order events, signature tampering/age, amount mismatch, immutable history/files, refunds before/after completion, partial refund/dispute suspension, token denial/expiry, no false email success/retry, recovery non-enumeration, pack delivery, public DTO privacy, missed-webhook reconciliation and backup restoration. Admin tests cover catalogue publication/confinement/packs/stats. Browser tests cover browsing/cart/direct purchase, automatic pending-payment refresh and explicit refunded/failed/expired states with API simulations. No live Stripe, real email, Peppol/tax system, HTTPS deployment, complete privacy programme or end-to-end print validation is claimed.

Primary technical references used: [Stripe webhook verification](https://docs.stripe.com/events/manage-webhook-endpoints), [Stripe fulfillment](https://docs.stripe.com/checkout/fulfillment), [Node SQLite](https://nodejs.org/api/sqlite.html).

## Corrections following manual tests — 23 October 2026

The visible storefront, download filename and new email subjects now use Small Things Lab. Technical Stripe store metadata, idempotency prefixes and existing browser storage keys retain their old identifiers to preserve compatibility; historical orders and sent emails are not rewritten. Emails have HTML and plain-text alternatives, a download button and readable purchase-time legal/consent sections rather than raw JSON. First-dispatch token refresh updates both alternatives.

The order page checks pending status every 2.5 seconds for up to about one minute, stops on a terminal state or navigation, and retains manual refresh. Failed/expired sessions preserve cart contents and grant no files. Refunded orders show their status only with a valid order token and offer no recovery of revoked files. Older tokens already deleted by the previous implementation cannot be restored; they receive a generic unavailable/expired/revoked message without disclosing order state.

These corrections sent no real email and created no new Stripe transaction. Automatic email sending remains disabled in local settings. The temporary Resend sender remains limited to the account's authorized address; production domain configuration is deferred.
